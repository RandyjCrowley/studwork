# Framework: environments and feature flags

> **A framework feature, always on: it is not a module and is not listed in `GameConfig.modules`.**

The framework knows which environment it runs in (Studio, the test place, live) and evaluates
feature flags from config per environment, with an optional live override read from Roblox's
experience configs. `StudWork.flags.isOn(name)` works on the server and the client. Added in
v1.7.0 (design: [module-api.md §23.1–§23.2](../module-api.md#23-additions-in-v170)).

This is a **framework feature, not a kit module**: it is always present, needs no entry in
`GameConfig.modules`, and does nothing until the game configures it. Why it lives in the framework
is in [decisions.md](../../decisions.md#v170-engagement-text-flags-localization). Code:
`packages/framework/shared/Env.luau` and `Flags.luau` (pure, both sides),
`packages/framework/server/FlagOverride.luau` (the live override).

## Quick start (flags)

A feature flag is a name in `GameConfig.flags`; a kit's `flag` config key points at it (a kill switch).
The harness must get the same `flags` as the game: the scaffold's `GameModule.spec` forwards
`Config.flags` (and the other GameConfig keys), so a flag you add to `Config` works in your specs.

```lua
-- GameConfig
flags = { notifications = { default = false, studio = true } },   -- off live until you flip it
config = { Notifications = { flag = "notifications", ... } },
-- game code, either side:
if StudWork.flags.isOn("notifications") then ... end
-- spec (mirrored by KitQuickStarts.spec.luau): pick the environment with env
local h = StudWork.test.harness({ modules = { Notifications }, env = "studio", flags = Config.flags, config = Config.config })
```

## Environments

```lua
-- GameConfig (generated from deploy.json by tools/sync-projects; see below)
environments = {
	test = { placeIds = { 2222222222 }, universeIds = { 1111111111 } },
	live = { placeIds = { 4444444444 }, universeIds = { 3333333333 } },
},
```

The environment is decided once per process, the same way on both sides:

1. `"studio"` when `RunService:IsStudio()` (any Studio session, including a Team Test).
2. `"test"` when `game.PlaceId` is in `environments.test.placeIds`.
3. `"live"` when `game.PlaceId` is in `environments.live.placeIds`.
4. `"test"` when `game.GameId` (the universe) is in `environments.test.universeIds` **and**
   `environments.live.universeIds` lists the live universe (so every place of the test experience,
   sub-places included, is test). **The test universe must be its own experience.** It is trusted
   only once the live universe is listed too, so it is known to be a different one (an id under
   both is a boot error): a hand-written config that put the live universe under `test` and listed
   no live universe would otherwise make every live server `"test"` and switch `testOnly` flags on in
   live. Until then `test.universeIds` is ignored (those servers run as live, the safe side), with
   one boot warning: `environments.test.universeIds is ignored until environments.live.universeIds
   lists the live universe ...`. A test place inside the live experience is listed by place id.
5. `"live"` otherwise: **an unknown place counts as live**, so a place nobody listed can never
   switch on test-only behaviour.

`environments.live` (`placeIds`, `universeIds`) is optional. It is used for a boot **warning** when
the place is in neither list ("place 123 isn't in environments; treating it as live") and for the
overlap check: **an id listed under both `test` and `live` is a boot error** (a deploy.json typo
that put the live place under test would otherwise switch every `testOnly` flag on in live).

**Where the ids come from.** `deploy.json` already holds each game's test and live place ids
([publishing.md](../publishing.md)). `tools/sync-projects` writes them to the game's
`src/shared/Config/Environments.luau` (generated, committed, `-- generated by tools/sync-projects`
header), and the template's Config sets `environments = require(script.Environments)`. Placeholder
ids (0, negative, non-integers, strings) are left out. The test universe id is written to
`test.universeIds` only when it differs from the live one: a test place inside the live experience
(same universe, its own place) is told apart by its place id, and the universe id goes under `live`
only. A test universe id is used only once the live one is filled in too (step 4 above). `tools/sync-projects` and its `--check` (part of `tools/lint`) fail when the test and live
place ids in `deploy.json` are equal (that place would be both), and `--check` fails when the file
is out of date or missing. Every game folder with a `deploy.json` and a `src/shared/Config` folder
gets the file; after pasting real ids into `deploy.json`, run `tools/sync-projects` and commit both.
A game may write `environments` by hand instead; the generated file is then not used (the boot
overlap check still applies). Hand-written ids must be positive integers, and `test` / `live` take
only `placeIds` and `universeIds` (a typo such as `placeId` is a boot error, not a silently live
place).

```lua
StudWork.env.name() -> "studio" | "test" | "live"     -- both sides, after StudWork.start
StudWork.env.placeId() -> number
StudWork.env.universeId() -> number                    -- game.GameId
ctx.env                                                -- the same table, on the server ctx
```

## Flags

```lua
-- GameConfig
flags = {
	newShop = { default = false, studio = true, test = true },          -- on in Studio and test, off live
	weeklyBoards = { default = true },                                   -- on everywhere
	debugPanel = { testOnly = true, default = false, studio = true, test = true },
	shopPrices = { default = true, serverOnly = true },                  -- never replicated
},
flagOverride = { enabled = true, keyPrefix = "flag_", refreshSeconds = 30 },
```

**Flag** fields:

| Field | Default | Meaning |
|---|---|---|
| `default` | required | the value where no environment field is given |
| `studio` / `test` / `live` | `default` | the value in that environment |
| `testOnly` | `false` | the flag can never be on in live: config that would make it on in live is a **boot error**, and a live override can't switch it on |
| `serverOnly` | `false` | its **value** isn't replicated: `isOn`, `onChanged` and `source` on the client error for it, and `all()` leaves it out. The definition is still in `GameConfig`, which clients have: to hide a flag's name and values too, declare it in `ServerConfig.flags` (below) |
| `override` | `true` | the live override may change this flag |
| `description` | none | shown by the console `flags` command |

Names match `^[%a][%w_]{0,47}$`. Values are booleans only.

**Hidden flags:** `ServerConfig.flags` (server-only config, never replicated) takes the same
fields; its flags are server-only by definition (`serverOnly` is implied). A name declared in both
`GameConfig.flags` and `ServerConfig.flags` is a boot error. **A flag whose name or values are
secret (an unannounced feature, a kill switch you don't want players to see) goes in
`ServerConfig.flags`**: `GameConfig` replicates to every client, so a `serverOnly` flag there still
shows its definition, `live`/`default` values included.

**Flags are for behaviour, not for trust.** A client-side flag value only changes what the client
shows. Anything a flag gates that matters (a purchase, a reward, an action) must be checked on the
server, where the flag is read again; a client that pretends a flag is on gains nothing.

**Boot errors** (reported with every other config error, failing closed):
- a `testOnly` flag whose live value (`live`, else `default`) is `true`:
  `flags.debugPanel is testOnly but would be on in live (set live = false or default = false)`;
- a flag without a boolean `default`, an unknown field, a bad name;
- an id listed under both `environments.test` and `environments.live`.

**Resolution** (the value `isOn` returns): the live override if one is set and allowed, else the
environment field, else `default`. In `"live"`, an override that would switch a `testOnly` flag on
is refused: a warning, the analytics event `FlagOverrideRefused`, and the flag stays off.

## The live override (Roblox experience configs)

Off unless `flagOverride.enabled = true`. The server reads Roblox's experience configs
(`ConfigService`, server-only), never the client:

- In a background thread after boot (boot never waits for it): `ConfigService:GetConfigAsync()`,
  in `pcall`. For each declared flag with `override ~= false`, the config key
  `<keyPrefix><name>` (e.g. `flag_newShop`): a boolean value is the override; a missing key or a
  non-boolean value means no override (one warning per key for a wrong type).
- `snapshot.UpdateAvailable` -> `snapshot:Refresh()`, at most once per `refreshSeconds`; plus a
  check of `snapshot.Outdated` every `refreshSeconds` (in case an update event was missed).
  Changed flags fire their `onChanged` handlers and are replicated.
- **Pick-up time:** Roblox publishes a config change to servers in roughly 15 s to 1 min; the
  framework applies it within `refreshSeconds` after that. No restart.
- If the first read fails, flags use config values and the read is retried with backoff (5, 10,
  ... up to `refreshSeconds` x 4). A later failure keeps the last values (Roblox's snapshot does
  the same).
- Only keys whose value changed since the last read are applied, so a Studio console override
  (`flags set`) stays until that flag's experience config changes. A missing key clears the
  flag's override (back to the config value).
- Configs are per experience: the test experience and the live experience each have their own,
  which is exactly the per-environment override you want. Staged config values apply only in
  Studio play sessions.
- Player-targeted configs (experiments) are not used: flags are server-wide.

## API

```lua
StudWork.flags.isOn(name) -> boolean            -- both sides; an undeclared name errors
StudWork.flags.onChanged(name, fn(on)) -> Connection
StudWork.flags.all() -> { [name]: boolean }     -- frozen; client: replicated flags only
StudWork.flags.source(name) -> "config" | "override"
ctx.flags                                       -- the same table on the server ctx
```

Before `StudWork.start`, `StudWork.flags` errors like `StudWork.use`. On the client, flags are
computed from the client's own copy of `GameConfig` and environment at start (the same pure
resolver), then overridden by the server's values in `state.framework.flags` once replicated, so
`isOn` never returns a value the config doesn't allow.

**Kit modules use flags as kill switches:** each v1.7.0 kit has a `flag` config key naming a game
flag; while that flag is off, the kit does nothing outward (no sends, no awards, no store traffic).
A kit never declares flags itself: the game owns the names.

**A testOnly feature: one pattern.** Declare the flag `{ testOnly = true, default = false, studio = true,
test = true }` (live can never switch it on), then:

- a **kit** (say Notifications only in test): name the flag in the kit's `flag` key and call the kit
  unconditionally. While the flag is off the kit refuses on its own (`suggestOptIn` returns
  `(false, "disabled")`, `submit` returns `false`), so game code needs no check;
- **your own code** (a debug panel, a dev-only command or button): gate it with
  `StudWork.flags.isOn(name)`.

Use `isOn` around a kit call only to skip game work the kit can't see (building a prompt UI, say).
Two flags for one feature drift apart: if game code checks `isOn`, check the same flag the kit
names.

**Console:** `flags` (list with value and source), `flags set <name> <true|false|clear>` (Studio
only: a local override for this server, like `ConfigService:SetTestingValue`).

## Replication

`state.framework.env = "studio" | "test" | "live"` and `state.framework.flags = { [name] = boolean }`
(every `GameConfig.flags` flag without `serverOnly`; never `ServerConfig.flags`), sent with the
framework state and on every change.

## Failure behaviour

| Situation | Behaviour |
|---|---|
| `ConfigService` unavailable or errors | config values; retried with backoff; no error to callers |
| Override has a wrong type | ignored, one warning per key |
| Override would enable a `testOnly` flag in live | refused, warning, `FlagOverrideRefused` analytics |
| Place not in `environments` | treated as live, one boot warning |
| `test.universeIds` without `live.universeIds` | the test universe is ignored (its servers run as live), one boot warning |
| An id in both `test` and `live` | boot error (and `sync-projects --check` fails for equal place ids in deploy.json) |
| Experience config read fails at boot | flags use config values; retried after 5, 10, 20 ... s (at most `refreshSeconds` x 4); boot never waits |
| A refresh fails | the last good values stay; the next `UpdateAvailable` or `Outdated` poll tries again |

## Tests (mocked)

- `harness({ env = "test" | "live" | "studio", placeId = n })` picks the environment (the harness
  injects its platform; on a real server those `StudWork.start` options are ignored with a warning,
  so a game can't start live as test);
  `StudWork.test.boot({ flags = ... })` returns the testOnly boot error.
- `StudWork.test.fakes.configService({ values = { flag_newShop = true } })` as
  `harness({ services = { ConfigService = fake } })`: `fake.set(key, value)` then
  `fake.publish()` fires `UpdateAvailable`; `h:tick(refreshSeconds)` applies it. `failNext(n)`
  makes `GetConfigAsync` error, `failRefreshNext(n)` makes `Refresh` error, and
  `publishQuietly()` publishes without the event (only the `Outdated` poll sees it).
- Specs: resolution order per environment; the boot error; an unknown place is live; override
  applied within `refreshSeconds`; a testOnly override refused in live and allowed in test;
  `serverOnly` not replicated and erroring on the client; `ServerConfig.flags` never replicated and
  a name clash is a boot error; a test universe id makes a sub-place test; a live universe listed
  under test (no live universe listed) still resolves live, testOnly off, with the warning; an
  overlapping id is a boot error; client resolver equals server resolver for the same config; the generated
  `Environments.luau` from a `deploy.json`, and `--check` failing on equal test and live ids
  (tools spec).
