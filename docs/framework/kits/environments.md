# Framework: environments and feature flags

The framework knows which environment it runs in (Studio, the test place, live) and evaluates
feature flags from config per environment, with an optional live override read from Roblox's
experience configs. `StudWork.flags.isOn(name)` works on the server and the client. Added in
v1.7.0 (design: [module-api.md §23.1–§23.2](../module-api.md#23-additions-in-v170)).

This is a **framework feature, not a kit module**: it is always present, needs no entry in
`GameConfig.modules`, and does nothing until the game configures it. Why it lives in the framework
is in [decisions.md](../../decisions.md#v170-engagement-text-flags-localization). Code:
`packages/framework/shared/Env.luau` and `Flags.luau` (pure, both sides),
`packages/framework/server/FlagOverride.luau` (the live override).

## Environments

```lua
-- GameConfig (generated from deploy.json by tools/sync-projects; see below)
environments = {
	test = { placeIds = { 2222222222 } },
	live = { placeIds = { 4444444444 } },
},
```

The environment is decided once per process, the same way on both sides:

1. `"studio"` when `RunService:IsStudio()` (any Studio session, including a Team Test).
2. `"test"` when `game.PlaceId` is in `environments.test.placeIds`.
3. `"live"` otherwise: **an unknown place counts as live**, so a place nobody listed can never
   switch on test-only behaviour.

`environments.live.placeIds` is optional and only used for a boot **warning** when the place is
in neither list ("place 123 isn't in environments; treating it as live").

**Where the ids come from.** `deploy.json` already holds each game's test and live place ids
([publishing.md](../publishing.md)). `tools/sync-projects` writes them to the game's
`src/shared/Config/Environments.luau` (generated, committed, `-- generated by tools/sync-projects`
header), and the template's Config sets `environments = require(script.Environments)`. Placeholder
ids (0, negative, non-integers) are left out. `tools/sync-projects --check` (part of `tools/lint`)
fails when the file is out of date. A game may write `environments` by hand instead; the
generated file is then not used.

```lua
StudWork.env.name() -> "studio" | "test" | "live"     -- both sides, after StudWork.start
StudWork.env.placeId() -> number
StudWork.env.universeId() -> number                    -- game.GameId
ctx.env                                                -- the same table, on the server ctx
```

## Flags

```lua
-- GameConfig
flags = {
	newShop = { default = false, studio = true, test = true },          -- on in Studio and test, off live
	weeklyBoards = { default = true },                                   -- on everywhere
	debugPanel = { testOnly = true, default = false, studio = true, test = true },
	shopPrices = { default = true, serverOnly = true },                  -- never replicated
},
flagOverride = { enabled = true, keyPrefix = "flag_", refreshSeconds = 30 },
```

**Flag** fields:

| Field | Default | Meaning |
|---|---|---|
| `default` | required | the value where no environment field is given |
| `studio` / `test` / `live` | `default` | the value in that environment |
| `testOnly` | `false` | the flag can never be on in live: config that would make it on in live is a **boot error**, and a live override can't switch it on |
| `serverOnly` | `false` | not replicated: clients see it as off and `isOn` on the client errors for it |
| `override` | `true` | the live override may change this flag |
| `description` | none | shown by the console `flags` command |

Names match `^[%a][%w_]{0,47}$`. Values are booleans only.

**Boot errors** (reported with every other config error, failing closed):
- a `testOnly` flag whose live value (`live`, else `default`) is `true`:
  `flags.debugPanel is testOnly but would be on in live (set live = false or default = false)`;
- a flag without a boolean `default`, an unknown field, a bad name.

**Resolution** (the value `isOn` returns): the live override if one is set and allowed, else the
environment field, else `default`. In `"live"`, an override that would switch a `testOnly` flag on
is refused: a warning, the analytics event `FlagOverrideRefused`, and the flag stays off.

## The live override (Roblox experience configs)

Off unless `flagOverride.enabled = true`. The server reads Roblox's experience configs
(`ConfigService`, server-only), never the client:

- In a background thread after boot (boot never waits for it): `ConfigService:GetConfigAsync()`,
  in `pcall`. For each declared flag with `override ~= false`, the config key
  `<keyPrefix><name>` (e.g. `flag_newShop`): a boolean value is the override; a missing key or a
  non-boolean value means no override (one warning per key for a wrong type).
- `snapshot.UpdateAvailable` -> `snapshot:Refresh()`, at most once per `refreshSeconds`; plus a
  check of `snapshot.Outdated` every `refreshSeconds` (in case an update event was missed).
  Changed flags fire their `onChanged` handlers and are replicated.
- **Pick-up time:** Roblox publishes a config change to servers in roughly 15 s to 1 min; the
  framework applies it within `refreshSeconds` after that. No restart.
- If the first read fails, flags use config values and the read is retried with backoff (5, 10,
  ... up to `refreshSeconds` x 4). A later failure keeps the last values (Roblox's snapshot does
  the same).
- Configs are per experience: the test experience and the live experience each have their own,
  which is exactly the per-environment override you want. Staged config values apply only in
  Studio play sessions.
- Player-targeted configs (experiments) are not used: flags are server-wide.

## API

```lua
StudWork.flags.isOn(name) -> boolean            -- both sides; an undeclared name errors
StudWork.flags.onChanged(name, fn(on)) -> Connection
StudWork.flags.all() -> { [name]: boolean }     -- frozen; client: replicated flags only
StudWork.flags.source(name) -> "config" | "override"
ctx.flags                                       -- the same table on the server ctx
```

Before `StudWork.start`, `StudWork.flags` errors like `StudWork.use`. On the client, flags are
computed from the client's own copy of `GameConfig` and environment at start (the same pure
resolver), then overridden by the server's values in `state.framework.flags` once replicated, so
`isOn` never returns a value the config doesn't allow.

**Kit modules use flags as kill switches:** each v1.7.0 kit has a `flag` config key naming a game
flag; while that flag is off, the kit does nothing outward (no sends, no awards, no store traffic).
A kit never declares flags itself: the game owns the names.

**Console:** `flags` (list with value and source), `flags set <name> <true|false|clear>` (Studio
only: a local override for this server, like `ConfigService:SetTestingValue`).

## Replication

`state.framework.env = "studio" | "test" | "live"` and `state.framework.flags = { [name] = boolean }`
(every flag without `serverOnly`), sent with the framework state and on every change.

## Failure behaviour

| Situation | Behaviour |
|---|---|
| `ConfigService` unavailable or errors | config values; retried with backoff; no error to callers |
| Override has a wrong type | ignored, one warning per key |
| Override would enable a `testOnly` flag in live | refused, warning, `FlagOverrideRefused` analytics |
| Place not in `environments` | treated as live, one boot warning |

## Tests (mocked)

- `harness({ env = "test" | "live" | "studio", placeId = n })` picks the environment;
  `StudWork.test.boot({ flags = ... })` returns the testOnly boot error.
- `StudWork.test.fakes.configService({ values = { flag_newShop = true } })` as
  `harness({ services = { ConfigService = fake } })`: `fake.set(key, value)` then
  `fake.publish()` fires `UpdateAvailable`; `h:tick(refreshSeconds)` applies it. `failNext(n)`
  makes `GetConfigAsync` error.
- Specs: resolution order per environment; the boot error; an unknown place is live; override
  applied within `refreshSeconds`; a testOnly override refused in live and allowed in test;
  `serverOnly` not replicated; client resolver equals server resolver for the same config; the
  generated `Environments.luau` from a `deploy.json` (tools spec).

## Not verifiable offline

`ConfigService` itself (real propagation time, staged values in Studio, behaviour while
disconnected), and `game.PlaceId` on real test and live places. Live checklist in the round
report.
